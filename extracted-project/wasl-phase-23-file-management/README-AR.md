# وصل — Phase 9: Backup & Restore Hardening

المرحلة دي بتستبدل نسخة PostgreSQL القديمة اللي كانت بتحمّل كل البيانات في الذاكرة (`store.data`) بطبقة repositories بتنّفذ استعلامات SQL مباشرة. مسارات HTTP وSocket.IO لا تتعامل مع `pool` ولا مع بيانات مخزنة في الذاكرة؛ بتتعامل مع واجهات التخزين فقط. وضع JSON المحلي ما زال متاحًا للتطوير والتوافق.

## متطلبات التشغيل

- Node.js 20 أو أحدث.
- PostgreSQL 14 أو أحدث عند اختيار وضع PostgreSQL.
- انسخ `.env.example` إلى `.env` واضبط `JWT_SECRET` على قيمة عشوائية قوية لا تقل عن 32 حرفًا.
- لا تضع ملف `.env` أو بيانات الاتصال بقاعدة البيانات في GitHub.

## تشغيل التطوير باستخدام JSON

```bash
npm install
cp .env.example .env
npm start
```

## تثبيت مخطط PostgreSQL جديد

استخدم قاعدة بيانات جديدة أو فارغة، ثم:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/001_init.sql
```

ثم اضبط `DATABASE_URL` في بيئة التطبيق. إذا كانت قاعدة بيانات مستضافة، فعّل `PGSSL=true` فقط عندما تكون شهادة TLS موثوقة ومهيأة بشكل صحيح.

## ترقية قاعدة Phase 4 القديمة

**لا تشغّل `101_migrate_phase4.sql` على قاعدة الإنتاج مباشرة.** خذ نسخة احتياطية واستعدها في قاعدة staging أولًا.

1. شغّل فحص القراءة فقط واحفظ المخرجات:
   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/100_preflight.sql
   ```
2. راجع الأعداد والمفاتيح وبادئات IDs والإيميلات المكررة. عينات الفحص تحذف بيانات حساسة مثل نصوص الرسائل ومسارات الملفات؛ الفحص لا يغيّر البيانات.
3. أنشئ الجداول العلائقية الجديدة في نفس قاعدة staging:
   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/001_init.sql
   ```
4. شغّل الترحيل في staging فقط:
   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/101_migrate_phase4.sql
   ```
5. تحقّق من العدادات والمراجع وملفات التخزين، ثم اختبر تسجيل الدخول والمحادثات والرسائل والمرفقات قبل التخطيط للإنتاج.

الترحيل يحتفظ بجداول `wasl_*` ولا يحذفها، ويتأكد من تطابق أعداد سجلات المصدر والهدف ومن عدم وجود بيانات هدف سابقة غير مسجلة كترحيل Phase 5. يتوقف عمدًا إذا لم تكن العضوية `memberIds` مصفوفة فيها عضوان على الأقل، أو وُجدت مراجع ناقصة/إيميلات مكررة/أعضاء مكررون. المحادثات ذات العضوين تُرحّل كمحادثات مباشرة، والأكبر تُرحّل كمجموعات؛ لا تتجاوز الخطأ قبل فهم البيانات.

## استيراد ملف JSON إلى مخطط PostgreSQL الجديد

بعد تطبيق `migrations/001_init.sql` على قاعدة فارغة:

```bash
npm run migrate:json-to-postgres -- ./data/wasl-store.json
```

الأداة ترفض قاعدة هدف غير فارغة، وتحافظ على IDs الحالية، وتتحقق من المراجع قبل الإدخال. تأكد أن مجلد `UPLOAD_DIR` وملفات المرفقات نُقلت بشكل منفصل؛ قاعدة البيانات لا تنقل الملفات الفعلية.

## المرحلة 6 — اختبارات API وCI

أُضيف اختبار HTTP متكامل يشغّل الخادم على JSON مؤقت ويختبر التسجيل والدخول وإنشاء محادثة مباشرة ومنع المستخدم الثالث من قراءة/إرسال الرسائل. أُضيف GitHub Actions مع PostgreSQL 16 لتطبيق المخطط وتشغيل اختبار التزامن الحقيقي عند push وpull request. هذه الاختبارات لا تُثبت ترحيل قاعدة Phase 4؛ الترحيل يحتاج نسخة staging تحتوي البيانات الفعلية.

## الاختبارات

```bash
npm test
```

الاختبارات الافتراضية تفحص العقود والبنية والثوابت الأمنية. اختبار PostgreSQL الحقيقي يُشغّل فقط عندما تضبط `TEST_DATABASE_URL` على **قاعدة اختبار منفصلة قابلة للتخلص منها** ومثبت عليها `migrations/001_init.sql`:

```bash
TEST_DATABASE_URL="postgresql://..." npm run test:postgres
```

لا تعتبر الاختبارات الثابتة إثباتًا أن اتصال PostgreSQL أو الترحيل نجح على قاعدة حقيقية؛ هذا يحتاج تشغيلًا فعليًا على staging.

## ما تغيّر

- إزالة `server/postgres-store.js` الذي كان يحتفظ بنسخة كاملة من البيانات في الذاكرة.
- إضافة `server/storage/pg/pool.js` مع `withTransaction`.
- إضافة repositories للمستخدمين والمحادثات والرسائل والمرفقات، مع adapter منفصل لوضع JSON.
- IDs ما زالت نصية وبالبادئات الحالية (`usr_`, `cnv_`, `msg_`, `att_`) وتُولّد في طبقة التخزين.
- إنشاء المحادثة المباشرة ذريًّا باستخدام unique index على زوج المستخدمين المرتّب.
- إضافة فحص signature أساسي للملفات المرفوعة، مع استمرار التحقق من العضوية قبل التنزيل والانضمام إلى غرفة Socket.IO.
- إضافة مخطط جديد وفحص read-only ومسار ترحيل منفصل من جداول Phase 4.

## حدود معروفة قبل الإنتاج

- لم يُنفّذ اختبار تكامل فعلي مع خادم PostgreSQL في بيئة البناء هذه؛ اختبار التزامن متخطّى ما لم يتم توفير `TEST_DATABASE_URL`.
- التخزين الفعلي للمرفقات ما زال على القرص المحلي؛ عند النشر متعدد النسخ يلزم تخزين مشترك أو S3-compatible مع خطة نسخ احتياطي تشمل قاعدة البيانات والملفات معًا.
- واجهة التطبيق الحالية تنشئ محادثات مباشرة فقط؛ دعم إنشاء المجموعات وصلاحيات إدارتها يحتاج endpoints وسياسات مستقلة.
- يلزم اختبار backup/restore وTLS والـ reverse proxy وإدارة الأسرار قبل الإنتاج.


## المرحلة 7 — فحوص الترحيل والاستعداد للإصدار

- أُضيفت حواجز توقف الترحيل عند اكتشاف محادثات مباشرة مكررة لنفس زوج المستخدمين أو مسارات تخزين مرفقات مكررة؛ لتفادي اصطدام القيود الفريدة وفقدان البيانات.
- أُصلح استعلام التحقق من مراجع أعضاء المحادثة باستخدام `CROSS JOIN LATERAL` بصورة صريحة.
- أُضيف `migrations/102_post_migration_checks.sql` لإظهار عدادات المصدر/الهدف وفحوص المراجع بعد الترحيل. شغّله على staging بعد نجاح `101_migrate_phase4.sql`.
- أُضيفت اختبارات ثابتة تتحقق من وجود حواجز الترحيل وفحوص ما بعده.

### تسلسل staging الموصى به

1. استعادة نسخة احتياطية من Phase 4 إلى قاعدة staging منفصلة.
2. تشغيل `100_preflight.sql` وحفظ المخرجات.
3. تطبيق `001_init.sql` على مخطط الهدف الفارغ.
4. تشغيل `101_migrate_phase4.sql`؛ سيتراجع تلقائيًا عن المعاملة عند أي خطأ.
5. تشغيل `102_post_migration_checks.sql` ومراجعة أن العدادات متطابقة وأن كل عدد `failures` يساوي صفرًا.
6. اختبار الدخول والرسائل والملفات وSocket.IO، ثم إجراء تجربة استعادة نسخة احتياطية.

**حدود التحقق:** اختبارات Node الثابتة لا تعادل اختبار SQL على PostgreSQL حقيقي. لم يتم في بيئة البناء هذه تشغيل خادم PostgreSQL؛ كما أن تثبيت حزم npm انتهى بمهلة زمنية. لذلك لا تعتبر المرحلة جاهزة للإنتاج قبل تشغيل CI واختبارات staging بنجاح.

## المرحلة 8 — التشغيل والنشر والنسخ الاحتياطي

### تشغيل نسخة Docker محلية

1. ثبّت Docker Engine وDocker Compose v2.
2. انسخ ملف البيئة النموذجي:
   ```bash
   cp .env.docker.example .env.docker
   ```
3. عدّل `POSTGRES_PASSWORD` و`DATABASE_URL` ليستخدما كلمة المرور نفسها، وضع `JWT_SECRET` عشوائيًا قويًا بطول 32 حرفًا على الأقل. لا ترفع `.env.docker` إلى Git.
4. شغّل التطبيق باستخدام ملف البيئة في مرحلة قراءة متغيرات Compose:
   ```bash
   docker compose --env-file .env.docker up --build -d
   docker compose --env-file .env.docker ps
   docker compose --env-file .env.docker logs -f app
   ```
5. تحقق من الخدمة:
   ```bash
   SMOKE_BASE_URL=http://127.0.0.1:3000 npm run smoke
   ```

الخدمة مربوطة على `127.0.0.1:3000` عمدًا؛ استخدم reverse proxy يدعم HTTPS أمامها في النشر العام، ولا تفتح منفذ Node مباشرة للإنترنت. مخطط `001_init.sql` يعمل تلقائيًا فقط عندما يكون مجلد بيانات PostgreSQL فارغًا. لا تُعد استخدام هذا الإعداد لترقية قاعدة Phase 4 موجودة.

### نسخ احتياطي واستعادة PostgreSQL

يتطلب الأمر أدوات PostgreSQL client (`pg_dump`, `pg_restore`) وصلاحيات مناسبة على قاعدة البيانات.

إنشاء نسخة احتياطية:
```bash
DATABASE_URL="$DATABASE_URL" BACKUP_DIR=./backups npm run backup:postgres
```

استعادة النسخة عملية مدمّرة محتملة على قاعدة الهدف، لذلك يلزم تأكيد صريح وتمرير الملفات الثلاثة من نفس وقت النسخ:
```bash
DATABASE_URL="$DATABASE_URL" \
BACKUP_FILE=./backups/wasl-YYYYMMDDTHHMMSSZ.dump \
UPLOADS_BACKUP_FILE=./backups/wasl-YYYYMMDDTHHMMSSZ.uploads.tar.gz \
BACKUP_MANIFEST_FILE=./backups/wasl-YYYYMMDDTHHMMSSZ.sha256 \
CONFIRM_RESTORE=YES npm run restore:postgres
```

الاستعادة تتحقق من SHA-256 ومن تطابق طوابع الملفات قبل لمس قاعدة البيانات. اختبرها على قاعدة مؤقتة أولًا، ثم اختبر تنزيل المرفقات. لا تعتمد على وجود ملفات النسخة وحده كدليل على قابلية الاسترجاع.

### تغييرات المرحلة 8

- أُضيف `Dockerfile` يعمل بمستخدم غير root، و`docker-compose.yml` مع PostgreSQL health check وvolumes دائمة.
- أُضيف `.env.docker.example`، ويجب عدم رفع الملف الفعلي `.env.docker` إلى المستودع.
- أُضيف `scripts/smoke.js` لفحص health route ورفض الوصول غير الموثق.
- أُضيفت سكربتات نسخ واستعادة PostgreSQL؛ الاستعادة تتطلب `CONFIRM_RESTORE=YES` وتظل بحاجة إلى تجربة على قاعدة مؤقتة.
- أُضيف فحص إعدادات الإصدار إلى الاختبارات، وخطوة بناء Docker إلى GitHub Actions.
- تم تحسين الإغلاق المنظم للخادم عند استقبال SIGTERM/SIGINT.

### حالة التحقق

تم تشغيل اختبارات Node المتاحة وفحوص syntax وstatic في بيئة التطوير. لم يكن Docker أو اتصال PostgreSQL حقيقي متاحًا في هذه البيئة، لذلك يلزم نجاح GitHub Actions — بما فيها اختبار التزامن وبناء الصورة — وتشغيل smoke test بعد النشر التجريبي قبل اعتبار الإصدار جاهزًا للإنتاج.


## المرحلة 9 — نسخ احتياطي واستعادة قاعدة البيانات والمرفقات

- `npm run backup:postgres` ينشئ ملف PostgreSQL بصيغة custom، وأرشيفًا منفصلًا لمجلد `UPLOAD_DIR`، وملف checksums.
- اضبط `UPLOAD_DIR` على نفس المسار الذي يستخدمه التطبيق، و`BACKUP_DIR` على مجلد محمي. لا ترفع النسخ إلى مستودع Git.
- قبل الاستعادة، تحقق من ملفات النسخ وقيم SHA-256 الموجودة في ملف `.sha256` باستخدام `sha256sum -c <manifest>`.
- الاستعادة تتطلب `BACKUP_FILE` و`UPLOADS_BACKUP_FILE` و`BACKUP_MANIFEST_FILE` و`CONFIRM_RESTORE=YES`. أمر `pg_restore --clean` مدمر لمحتويات قاعدة الهدف؛ استخدم قاعدة staging أولًا.
- يتم التحقق من checksum لكل ملف ومن أن الملفات الثلاثة من نفس النسخة قبل استعادة قاعدة البيانات، ويُرفض الأرشيف الذي يحتوي مسارات غير آمنة أو روابط/عناصر خاصة.
- ملفات المرفقات تُستخرج في مجلد مؤقت. بعد نجاح استعادة قاعدة البيانات، تُنسخ الملفات فوق `UPLOAD_DIR`؛ الملفات القديمة غير الموجودة في الأرشيف لا تُحذف تلقائيًا.
- لضمان تطابق زمني بين سجلات قاعدة البيانات والملفات، أوقف الكتابة/التطبيق أثناء أخذ النسخة أو استخدم آلية snapshot منسقة. اختبارات هذه المرحلة تتحقق من إعدادات السكربتات، ولا تعني أن backup/restore نُفّذ على قاعدة فعلية.


## المرحلة 10 — تشديد أمان الاستعادة

- أصبح ملف `.sha256` إلزاميًا في سكربت الاستعادة؛ تُفحص بصمات قاعدة البيانات وأرشيف المرفقات قبل أي تغيير على الهدف.
- يرفض السكربت خلط ملفات من نسخ مختلفة، أو manifest غير مطابق، أو أرشيف مرفقات يحتوي روابط رمزية/صلبة أو عناصر خاصة.
- هذا تحسين دفاعي واختبارات ساكنة؛ لم يتم تنفيذ استعادة على PostgreSQL حقيقي في بيئة العمل الحالية.

### تحسينات المرحلة 11 — سلامة النسخ الاحتياطي وCI

- سكربت النسخ الاحتياطي يرفض الكتابة فوق أي نقطة استعادة موجودة بنفس التوقيت، بدل استبدالها بصمت.
- ملف SHA-256 يُنشر في النهاية باعتباره علامة اكتمال النسخة؛ وعند فشل خطوة، يحذف السكربت مخرجات التشغيل الجزئية التي أنشأها.
- تمت إضافة اختبارات آلية لنجاح إنشاء مجموعة النسخ، ورفض الكتابة فوق نسخة سابقة، وتنظيف المخرجات بعد فشل الأرشفة.
- خط CI يفحص صياغة سكربتات shell بجانب JavaScript.
- ما زال مطلوبًا تشغيل اختبار PostgreSQL والاستعادة الفعلية على قاعدة اختبار قابلة للتخلص منها؛ الاختبارات المحلية التي لا تملك قاعدة PostgreSQL لا تثبت نجاح الاستعادة الحقيقية.

## المرحلة 12 — استعادة ملفات المرفقات بشكل قابل للتراجع

- لا تستخدم الاستعادة `cp -R` فوق مجلد المرفقات الموجود؛ بل تستخرج الأرشيف إلى مجلد مؤقت بجانب `UPLOAD_DIR` ثم تستبدل شجرة الملفات بالكامل، حتى لا تبقى ملفات قديمة غير موجودة في النسخة المستعادة.
- يُحتفظ بمجلد المرفقات السابق داخل مساحة staging حتى تنجح عملية `pg_restore`. إذا فشل أمر استعادة PostgreSQL، يحاول سكربت الاستعادة إعادة مجلد المرفقات السابق تلقائيًا.
- أُضيف اختبار انحدار يحاكي فشل `pg_restore` ويتأكد من رجوع الملفات القديمة وعدم ترك الملفات الجديدة في المجلد المستعاد.
- **حدّ مهم:** PostgreSQL ونظام الملفات لا يشتركان في معاملة ذرية واحدة. فشل `pg_restore` بعد أن يكون قد عدّل بعض جداول قاعدة البيانات قد يترك قاعدة الهدف بحاجة إلى إعادة استعادة أو تحقق يدوي، حتى لو رجعت ملفات المرفقات القديمة. لذلك أوقف حركة المرور، واستخدم قاعدة staging، وشغّل smoke tests قبل إعادة فتح التطبيق.
- نتائج التحقق المحلية لهذه المرحلة: `npm test` نجح في 21 اختبارًا، مع تخطي اختبارين لأن اعتماديات التطبيق غير متاحة محليًا و`TEST_DATABASE_URL` غير مضبوط. فحوص الصياغة والفحص الساكن وفحص shell نجحت. لم تُجرَ استعادة على قاعدة PostgreSQL حقيقية في هذه البيئة.


## المجموعات

## المرحلة 15 — دورة حياة الرسائل والقراءة

تضيف هذه المرحلة واجهات لتعديل الرسائل النصية (لصاحب الرسالة فقط)، وحذفها منطقيًا، والرد داخل المحادثة، وإعادة توجيه الرسائل النصية مع حفظ مرجع المصدر، وتثبيت الرسائل (في المجموعة للمالك/المشرف فقط)، وإشعارات القراءة الفورية. أحداث Socket.IO الجديدة: `message:updated` و`message:deleted` و`messages:read`.

### ترقية PostgreSQL من المرحلة 14

قبل تشغيل النسخة الجديدة على قاعدة بيانات موجودة، خذ نسخة احتياطية ثم نفّذ `migrations/103_phase15_message_features.sql` بحساب قاعدة البيانات المخصص للتطبيق. المخطط الجديد `migrations/001_init.sql` يتضمن أيضًا الجداول والأعمدة اللازمة للتثبيت الجديد. لا تشغّل `001_init.sql` فوق قاعدة بيانات قائمة دون اتباع مسار الترحيل الموثق.

### حدود السلوك الحالي

- حذف الرسالة منطقي ويُبقي مكانها في سجل المحادثة مع نص «تم حذف هذه الرسالة».
- تعديل الرسائل ذات المرفقات غير مسموح في هذه المرحلة؛ يمكن حذفها منطقيًا بواسطة صاحبها.
- إعادة التوجيه تحفظ مرجع الرسالة المصدر وتعيد توجيه النص الذي يظهر في مربع الكتابة؛ لا تنسخ ملف المرفق نفسه.
- في المجموعات، قراءة الرسائل تُسجل لكل مستخدم على الرسائل السابقة للرسالة المستهدفة.
- واجهة إدارة الرسالة الحالية تعتمد قائمة خيارات بسيطة عبر المتصفح؛ يمكن تحسينها لاحقًا إلى قائمة مخصصة أكثر أناقة.


## المرحلة 16 — الحضور والمزامنة والإشعارات

- حالة الاتصال تُحسب من اتصالات Socket.IO الفعلية، وتظل الحسابات متصلة طالما بقي جهاز واحد على الأقل متصلًا.
- حفظ `last_seen_at` في PostgreSQL، وحفظ `lastSeenAt` في تخزين JSON عند انقطاع آخر جهاز.
- أحداث `presence:snapshot` و`presence:update` تعرض الحالة لجهات الاتصال المشتركة في المحادثات فقط.
- أحداث `typing:start` و`typing:stop` تتحقق من عضوية المحادثة وتحد من معدل إشارات الكتابة.
- مزامنة الرسائل لأجهزة المرسل الأخرى عبر `message:sync`، وإشعارات داخل الجلسة عبر `notification:new`.
- واجهة المتصفح تعرض حالة الاتصال والكتابة، وتستخدم إشعارات النظام فقط إذا كان المستخدم قد منح إذن المتصفح مسبقًا.
- الترحيل لقواعد PostgreSQL الموجودة: `migrations/104_phase16_presence.sql` بعد ترحيلات المراحل السابقة.

**حدود النشر:** حالة الاتصال الفورية محفوظة في ذاكرة عملية Node.js الحالية. عند تشغيل أكثر من نسخة خادم، يلزم Socket.IO shared adapter ومخزن presence مشترك (مثل Redis) حتى تكون الحالة دقيقة بين النسخ. الإشعارات هنا فورية وليست صندوق إشعارات دائمًا أو Push Notifications عند إغلاق التطبيق.


## المرحلة 17 — الإشعارات الدائمة والخصوصية والجلسات

- الإشعارات تُحفظ للمستلم في التخزين المحلي أو PostgreSQL، مع قائمة صفحات، وعدّاد غير المقروء، ووضع إشعار كمقروء، وقراءة الكل، والحذف.
- إعدادات الخصوصية: `showLastSeen` و`showOnlineStatus` تقبل `everyone` أو `contacts` أو `nobody`، و`notificationsEnabled` قيمة منطقية.
- إدارة الجلسات: `GET /api/auth/sessions`، وإلغاء جلسة عبر `DELETE /api/auth/sessions/:sessionId`، وإلغاء بقية الجلسات عبر `POST /api/auth/sessions/revoke-others`، وتسجيل الخروج عبر `POST /api/auth/logout`.
- رموز الدخول الجديدة مرتبطة بسجل جلسة قابل للإلغاء. بعد الترقية سيحتاج المستخدمون إلى تسجيل الدخول مرة أخرى لأن الرموز القديمة لا تحتوي على معرّف جلسة قابل للإلغاء. لذلك يلزم تطبيق ترحيل `migrations/105_phase17_notifications_privacy_sessions.sql` قبل نشر إصدار المرحلة 17 على PostgreSQL.
- إعدادات الخصوصية الافتراضية تُظهر الحضور للجميع وتسمح بالإشعارات. تعطيل الإشعارات يمنع إنشاء إشعارات جديدة ولا يحذف السجل السابق.
- إشعارات هذه المرحلة محفوظة داخل التطبيق وتصل لحظيًا عبر Socket.IO عند اتصال الجهاز؛ لا تتضمن خدمة Push خارجية مثل FCM.
- إعداد `contacts` يعامل حاليًا على أنه الأشخاص المشاركون مع المستخدم في محادثة مشتركة، لأن المشروع لا يملك دفتر جهات اتصال منفصلًا.

## المرحلة 21 — صور الحساب المتزامنة

- رفع صورة الحساب عبر `POST /api/account/avatar` باستخدام `multipart/form-data` والحقل `avatar`، مع جلسة دخول صالحة.
- إزالة الصورة عبر `DELETE /api/account/avatar`، وعرضها عبر `GET /api/account/avatar/:userId` للمستخدمين المسجلين فقط.
- الأنواع المسموحة PNG وJPEG وWebP، بحد أقصى 1 MiB، مع التحقق من توقيع الملف الفعلي على الخادم؛ لا يُعتمد على `Content-Type` المرسل من المتصفح وحده.
- تخزين الملفات في `UPLOAD_DIR/profile-avatars` خارج مجلد الويب العام، بأسماء عشوائية، مع `nosniff` وترويسات تخزين خاصة.
- أضيفت أعمدة `avatar_storage_name` و`avatar_mime_type` إلى المخطط الجديد، وترحيل `migrations/106_phase21_profile_avatars.sql` لقواعد البيانات القائمة.
- طبّق الترحيل 106 على PostgreSQL القائم قبل تشغيل النسخة الجديدة. خُذ نسخة احتياطية قبل الترحيل.
- في نشر متعدد النسخ، يجب أن يكون `UPLOAD_DIR` على تخزين ملفات مشترك أو خدمة تخزين كائنات؛ التخزين المحلي داخل الحاوية وحده لا يضمن مشاركة الصور بين نسخ الخادم.
- اختبارات البيئة الحالية لا تثبت تكامل HTTP/PostgreSQL حقيقيًا ما لم تتوفر الاعتماديات وقاعدة اختبار. راجع `PHASE21-REPORT.md` للنتائج الدقيقة.


## المرحلة 22 — مركز التخزين وتحسين الصور

- صفحة إعدادات **مساحة التخزين** تعرض إجمالي المرفقات المرفوعة بواسطة الحساب وصورة الحساب، عدد الملفات، المساحة المستخدمة والمتبقية.
- نقطة `GET /api/account/storage` تتطلب تسجيل الدخول، وتعيد قيمًا رقمية للواجهة دون كشف مسارات الملفات الداخلية.
- حد التخزين الافتراضي للحساب 100 MiB ويمكن ضبطه عبر `ACCOUNT_STORAGE_QUOTA_MB` (الحد الأدنى 10 MiB). حد الملف الفردي ما زال يتحكم به `MAX_UPLOAD_MB`.
- يتم رفض مرفق جديد برسالة `413` ورمز `ACCOUNT_STORAGE_QUOTA_EXCEEDED` إذا تجاوز الاستخدام الحالي مع الملف الجديد الحد؛ يظل فحص الحصة مبنيًا على القراءة ثم الكتابة، لذلك على الاستضافات متعددة النسخ أو الرفع المتزامن بكثافة يُنصح بتطبيق حجز حصة ذري في قاعدة البيانات قبل اعتباره حدًا ماليًا/صارمًا.
- ضغط صورة الحساب يتم في المتصفح إلى JPEG بعرض/ارتفاع أقصى 512px وجودة 84% قبل الإرسال، ثم يستمر الخادم في فحص توقيع الملف. لا يعتمد الخادم على ضغط المتصفح كحاجز أمني.
- `GET /api/account/storage` لا ينظف الملفات اليتيمة ولا يضمن اكتشاف ملفات أزيلت يدويًا من القرص؛ لا يزال تنظيف الوسائط إجراءً تشغيليًا منفصلًا.
- الإعدادات في `.env.example` و`.env.production.example` تتضمن `ACCOUNT_STORAGE_QUOTA_MB=100`.
